# Badminton Skills Coach v3 产品与技术规格

- 状态：`accepted`
- 日期：2026-08-31
- 产品确认：2026-08-31，三项决策全部确认
- 基线：`develop@b04b103`（v2.1.5-dev.1，稳定版为 v2.1.4）
- 实施分支：`codex/v3-evidence-refactor`
- 适用范围：维护端语料流水线、本地审核台、公开运行时、Codex Skill 回答契约与评测发布

## 1. 一句话定义

Badminton Skills Coach 是一个离线、证据驱动的 Codex Skill：用户用自然语言描述羽毛球技术、步法、战术、器材或训练问题，系统先诊断问题边界，再基于刘辉公开视频中经过核对的教学证据给出解释、练习建议、时间戳和原视频链接。

本项目独立开发，不是刘辉本人，不代表刘辉、抖音、哔哩哔哩或任何发布者的认可或背书。

## 2. 我对当前项目的理解

### 2.1 用户价值

用户真正需要的不是“搜到几条标题相似的视频”，而是：

1. 把症状、动作、来球条件、场区、主动/被动、正反手和单双打场景分开；
2. 区分用户观察到的现象与未经证实的原因；
3. 只陈述有原视频支持的技术结论，并保留适用条件和排除边界；
4. 给出能直接观看、带时间戳且说明“为什么值得看”的视频；
5. 证据不足时明确指出缺口，而不是靠常识、原始 ASR 或模型补全。

### 2.2 当前系统形态

当前仓库同时包含两类产品：

- **维护端系统**：发现公开视频、下载或读取本地媒体、转写、分类、建立知识与检索产物、审核反馈、运行评测并发布 Skill。
- **公开运行时 Skill**：一个可复制安装的目录，使用只读 SQLite 与确定性规则检索证据，生成受约束的 answer packet，再由模型组织成最终回答。

稳定版运行时不需要 OpenAI API key 或转写工具。原始媒体、原始转写、私有反馈和本地缓存不进入发行包。

### 2.3 当前数据事实

以 `data/knowledge/build_manifest.json` 和当前发布产物为准：

| 指标 | 当前值 |
| --- | ---: |
| 已处理视频 | 1,017 |
| 可回答视频 | 959 |
| `primary` | 784 |
| `supplemental` | 175 |
| 含完整转写片段的可回答视频 | 766 |
| 仅保留受限证据窗口的 B 站视频 | 174 |
| 依赖人工视觉摘要的视频 | 19 |
| 明确标记为 reviewed transcript 的视频 | 6 |
| 已审核 evidence atoms | 24 |
| 回答质量用例 | 57 |
| 当前确定性评测套件 | 14 套、74 个基线指标、0 回归 |

这些数字说明 v2 已经有成熟的采集、检索、回答约束和发布工程，但“可检索”与“逐字稿已经对照原视频完整核正”、“主张已经由领域审核者批准”仍是不同事实。v3 的核心不是再叠一层检索规则，而是建立可审计的正式证据链。

### 2.4 v2 必须保留的能力

- 来源身份、canonical URL、重复/镜像处理和稳定视频 ID；
- `primary` / `supplemental` / `none` 的证据资格边界；
- query planning、语义准入、候选/合成/展示分层；
- 每条结论独立的证据 allowlist；
- 最多 3 个来源支撑一条结论、最多 5 条核心视频且不凑数；
- answer packet、内容哈希、最终答案审计和稳定 `V1…Vn` 引用；
- 私有反馈与公开最小信号隔离；
- 只读 SQLite、可复现构建、显式发行白名单、SBOM、签名标签和 CI 门禁；
- Python 3.10+、macOS/Linux/Windows 的可移植安装。

## 3. v3 要解决的问题

### 3.1 核心问题

v2 的主要知识单元仍然是“视频记录 + 转写片段/摘要 + 检索规则”。这会产生四类风险：

1. **ASR 正确性不可继承**：自动归一化、旧状态名或“通过工程质量门”都不等于逐句听过原视频。
2. **证据边界不够正式**：检索命中的上下文可能包含相邻但不支持当前结论的内容。
3. **技术主张与来源耦合不清**：同一视频可包含多个条件不同的教学事件；同一主张也可能由多个视频共同支持。
4. **修改传播不可审计**：转写、时间戳或媒体发生变化时，依赖它的摘要、事件、主张和评测必须自动失效。

### 3.2 产品目标

v3 以“**经原视频核对的正式转写 + 对应原视频**”为来源事实，建立从来源到回答的完整证据链：

`原视频 → 原始 ASR → 校正候选 → 正式转写 → 教学事件 → 语义主张 → 已发布证据 → answer packet → 最终回答`

成功标准不是“所有转写都能搜”，而是：每个最终技术句子都能追溯到一个或多个已核对的、带时间边界的教学事件，并能解释适用条件、排除条件与置信上限。

### 3.3 非目标

- 不训练或微调基础模型；
- 不把新转写写入模型权重或 Codex 会话记忆；
- 不自动把 ASR、标题、分类、模型摘要或旧 evidence atom 升格为正式主张；
- 不上传用户数据、原视频、完整转写或私有审核记录；
- 不在仓库或发行包中重新分发原视频/音频；
- 不做通用羽毛球百科，也不冒充刘辉；
- 不为了数量目标制造重复、无价值或边界不清的主张；
- v3 未通过切换门禁前，不改变稳定 v2 的回答路径。

## 4. 术语与权威层级

| 名称 | 含义 | 能否直接支持回答 |
| --- | --- | --- |
| `SourceVideo` | 平台原生视频身份、canonical URL、镜像关系和来源元数据 | 否 |
| `MediaAsset` | 本地用于审核的媒体文件及 SHA-256；不进 Git | 否 |
| `RawASR` | 固定配方生成的不可变原始转写 | 否 |
| `CanonicalCandidate` | 规则或模型提出的文字、标点、切分、时间对齐候选 | 否 |
| `FormalTranscript` | 审核者逐段核对并完整播放对应媒体后确认的正式投影 | 只能作为来源事实，不能独立代表羽毛球判断 |
| `VideoSummary` | 审核者确认的视频主题、场景、覆盖与不覆盖边界 | 只能辅助选材和限定范围 |
| `TeachingEvent` | 某个时间区间内实际说出、展示或共同表达的教学事件 | 是，前提是已 source verified |
| `SemanticClaim` | 从教学事件归纳出的结构化技术主张 | 只有 `published` 可进入回答 |
| `SemanticFrame` | 用户问题的结构化场景：症状、动作、场区、正反手、主动/被动等 | 不是证据，只用于匹配 |
| `Publication` | 从私有审核账本净化导出的公开、确定性、可复现数据 | 是正式运行时唯一构建输入 |
| `AnswerPacket` | 一次回答获准使用的主张、证据、边界、视频和缺口 | 是模型组织回答的唯一事实边界 |

这里有两个必须分开的判断：

- **来源核对（source verification）**：原视频在某段时间实际说了或展示了什么；
- **领域批准（domain approval）**：这些事实能否归纳成某个羽毛球结论，以及该结论适用于什么场景。

自动工具可以准备候选、发现异常和验证结构，但不能声称这两类人工判断已经发生。

## 5. 不可妥协的证据不变量

以下规则 fail closed；任何一条不满足，相关内容不能进入正式回答：

1. 原始 ASR、完整 raw transcript、标题、标签、搜索分数和模型摘要永远只是候选，不是回答证据。
2. 自动纠错只生成 `suggestion`。即使是高精度错词替换，也必须在审核界面可见并绑定规则版本；不能静默继承人工状态。
3. 正反、内外、先后、否定、击球点、线路、数字、正反手和主动/被动等意义轴不得自动批准。
4. 正式转写必须覆盖原有全部片段、人工插入的漏句、删除的误识别和修正后的时间边界；随后还要单独确认完整媒体已播放、漏句与时间完整性已检查。
5. “所有现有片段都处理了”不等于“没有漏掉整句话”；完整媒体确认是独立门禁。
6. `0` 段 ASR 不证明视频没有口播。必须完整播放媒体，补录听到的内容，或显式确认无可用口播。
7. 语言主张必须有正式转写窗口；视觉主张必须记录实际核对过的画面区间/帧；多模态主张必须同时满足两者。
8. 每次审核决定都绑定来源媒体哈希（若可得）、raw ASR 哈希、规则版本、时间范围和当前正式投影哈希。
9. 转写文本、插入/删除、时间边界或来源媒体发生变化时，依赖旧投影的教学事件、主张与评测绑定自动变为 `stale`。
10. 旧 v2 的 24 个 atoms、57 个质量用例和所有历史状态只作为候选输入，不能继承 `source_verified` 或 `domain_approved`。
11. 抖音和 B 站没有平台权重；镜像只算一个来源身份，同时保留 canonical 与 alternate URLs。
12. 只有 `published` 的语义主张可进入 v3 正式检索；草稿、驳回、过期、仅候选或仅 v2 的内容不得回退补洞。
13. 一条主张只能使用自己绑定的支持事件；证据授权不能跨主张、跨问题或跨轮次转移。
14. 回答必须保留来源身份、证据模式、置信上限、适用/排除边界、时间戳和稳定 `V1…Vn` 映射。
15. 证据不足时输出缺口或提出一个高价值澄清问题，不使用通用模型知识伪装成来源结论。

## 6. 产品范围与首批切片

### 6.1 全量范围

最终范围是当前 959 条可回答视频。每条来源身份都必须有明确状态，不能通过“只统计已有转写”绕过缺口。

### 6.2 六类影子试点

第一阶段沿用当前知识分类中覆盖面最大、现有评测最充分的六类：

1. 正手后场；
2. 反手后场；
3. 网前；
4. 发接发；
5. 步法；
6. 双打。

试点先在 shadow runtime 中运行。候选选材必须先对全部可回答来源做全局路由和去重，再按主题形成审核队列；不能让先处理的主题抢走跨主题视频，也不能按平台配额凑数。

“每主题约 20 条高价值来源”只作为首轮人工工作量预算，不是发布质量代理。旧原型中的“每主题至少 50 条主张”不作为硬门禁；主张数量不能替代覆盖率、正确性和边界完整性。

### 6.3 切换策略

- v3 试点未全部通过前，正式回答继续使用 v2；
- 六类试点通过后一次性切换到 v3，避免同一复合问题在两套证据语义之间产生不一致；
- 非试点主题继续使用 v2，并在 answer packet 中明确运行时版本；
- 全部 959 条完成迁移且回归通过后，才讨论删除 v2 路径。

## 7. 数据边界与目录设计

### 7.1 私有维护平面

默认位于 Git 忽略的 `.local/v3/`，建议结构如下：

```text
.local/v3/
├── media/sha256/              # 原视频/音频，按内容哈希存储
├── asr/raw/                   # 不可变 raw ASR
├── candidates/                # 规范化、对齐、摘要和主张建议
├── review/review-ledger.sqlite3
├── review/autosave/           # 崩溃恢复草稿
├── holdout/                   # 密封问题与逐例结果
└── cache/                     # 可删除、可重建缓存
```

私有平面允许保存完整正式转写，但所有记录必须指向内容哈希，不能只依赖可变文件路径。

### 7.2 公开仓库平面

```text
schemas/v3/                    # JSON Schema / SQL schema
config/v3/                     # 规则、质量门和版本化配置
data/v3/source-inventory.json  # 净化后的来源与输入覆盖清单
data/v3/publication.json       # 已批准的最小公开投影
data/v3/build-manifest.json    # 阶段输入/输出哈希和构建指纹
scripts/v3/                    # 纯函数核心、CLI、构建与审计
review-ui/                     # 本地审核界面静态资源
```

### 7.3 发行包边界

v3 发行包默认只包含：

- 已发布主张及结构化条件；
- 支持它们的最小、带时间戳证据窗口；
- 来源视频 ID、canonical/alternate URLs 和观看理由；
- 检索索引、规则版本、构建与审核指纹；
- 回答运行与审计代码。

默认不包含原视频、音频、raw ASR、完整正式转写、私有审核笔记、审核者个人信息和密封 holdout 原文。完整正式转写可以作为私有构建依据，但不是默认公开发行内容。

## 8. 核心数据模型

### 8.1 稳定身份

- `source_id`：平台原生 ID 与发布者身份组成的稳定来源身份；
- `media_asset_id`：媒体 SHA-256；
- `transcript_revision_id`：`source_id + raw_asr_sha256 + rule_version + formal_projection_sha256`；
- `segment_id`：来源片段身份，不因文字改写而复用到另一原始片段；
- `teaching_event_id`：来源身份 + 时间范围 +正式投影哈希；
- `claim_id`：稳定语义 ID，不使用数组位置；
- `publication_id` / `runtime_fingerprint`：规范 JSON 的内容哈希。

用户可见的 `V1…Vn` 是一次回答内的稳定展示标签；内部证据 ID 在不同回答和构建间保持可追溯。

### 8.2 审核账本

审核采用 append-only event ledger。每条事件至少记录：

- entity type / entity ID；
- action、from state、to state；
- reviewer ID 与时间；
- base fingerprint 与 payload fingerprint；
- 结构化修改内容和可选说明；
- 被替代事件 ID。

当前状态是账本的可重建投影，不直接覆盖历史。草稿可更新；正式提交只能追加新修订。

### 8.3 状态机

正式转写：

```text
missing → raw_available → candidate → in_review → source_verified
                                      ↘ rejected
source_verified --(输入或投影变化)--> stale
```

语义主张：

```text
draft → source_verified → domain_approved → published
  └──────────────→ rejected                 → withdrawn
任一依赖失效 → stale
```

`source_verified`、`domain_approved` 和 `published` 是三次不同的显式动作，不能由同一个自动命令连跳。

## 9. 私有语料流水线

### 9.1 阶段

1. **发现与身份解析**：读取平台索引，建立 source identity 和镜像关系。
2. **媒体准备**：按需下载或定位本地媒体，记录来源、时长、音视频流与 SHA-256。
3. **原始转写**：使用锁定的模型、版本、参数、语言与音频预处理配方；保存不可变结果。
4. **候选规范化**：只生成建议，记录每次替换的规则和置信；不得覆盖 raw ASR。
5. **时间对齐**：生成词/句级候选时间边界；无法对齐的内容保持显式缺口。
6. **转写审核**：对照原视频接受、保留、改写、删除误识别、插入漏句或调整时间。
7. **完整性确认**：全部片段处理后完整播放媒体，单独确认覆盖、时序与漏句。
8. **视频摘要**：确认主题、场景、覆盖项、不覆盖项或 `none_identified`，也可标记不可用。
9. **教学事件**：绑定正式转写与/或画面观察，给出精确时间边界和证据模式。
10. **语义主张**：填写症状、条件、机制、纠正方向、排除项、置信和支持事件。
11. **净化发布**：只导出完整走过状态机的内容，扫描私有字段和旧指纹。
12. **确定性构建**：构建只读 runtime store、索引、manifest、SBOM 和发行包。

### 9.2 增量构建

每个阶段声明版本、代码输入、数据输入、输出和内容哈希。只有受影响的下游阶段重建；任何缓存都可以删除并从声明输入复现。构建图本身进入仓库，私有媒体只以哈希和可用性状态出现。

### 9.3 恢复路径

对于当前 959 条可回答来源，按以下顺序恢复：

1. 已有 raw ASR 与记录哈希一致：进入候选生成，不继承批准状态；
2. raw ASR 丢失但媒体哈希一致：使用固定配方重转写，作为新候选版本；
3. 媒体存在但无历史媒体哈希：允许新候选，但明确无法证明历史字节一致；
4. 转写和媒体都缺失：保持 `input_missing`，不能从标题、摘要或旧窗口反推逐字稿；
5. 旧 v3 worktree 的恢复审计与本地文件只能作为候选，必须在新基线重新验证哈希和覆盖。

## 10. 本地审核台

### 10.1 运行与安全

- 默认仅监听 `127.0.0.1`，使用随机会话令牌和 CSRF 防护；
- 不加载远程脚本、字体、分析或遥测；
- 原视频优先读取本地媒体；无法取得媒体时可显式打开来源页面，但必须记录审核依据；
- 保存草稿不代表正式审核；正式操作要求审核者身份和“本人核对”确认；
- 自动保存、崩溃恢复、撤销/重做和修订历史均在本地。

### 10.2 工作视图

审核台提供五个主视图：

1. **来源队列**：教学/非教学、主题候选、镜像、媒体与转写可用性；
2. **转写校对**：视频播放器、当前片段、相邻上下文、候选/正式文本、时间边界；
3. **风险队列**：意义敏感词、长静音、重叠、时间倒序、疑似漏句和自动替换；
4. **事件与主张**：教学事件、语言/视觉/多模态证据、条件、排除和支持关系；
5. **评测与历史**：问题 frame、必答/禁答主张、修订 diff、过期依赖和构建指纹。

### 10.3 交互原则

- 机器 suggestion 与人工 response 在视觉和数据结构上分离；
- Focus view 用于逐条听看，Bulk view 只用于筛选、分派和低风险分类；
- 禁止批量批准完整转写、意义敏感修改、教学事件或领域主张；
- 支持键盘播放/暂停、前后跳转、设定起止点和快速切换相邻片段；
- 每次正式提交前显示它会批准什么、不会批准什么，以及哪些下游对象将失效。

## 11. v3 检索与回答契约

### 11.1 正式路径

```text
用户问题
→ query understanding
→ semantic frame / 必答子问题 / 待澄清项
→ 仅检索 published claims
→ 条件、排除、来源和证据模式过滤
→ 确定性排序与去重
→ claim-scoped evidence allowlist
→ answer packet
→ 模型组织
→ 最终答案审计
```

模型只能看到 answer packet，不读取私有账本、raw ASR、完整候选转写或 packet 外搜索结果。

### 11.2 回答行为

- 先给诊断，再给机制、修正方向和练习；
- 分开表达“视频明确支持”与“基于多条证据的受限归纳”；
- 每条技术结论最多使用 3 个来源不同的最强证据；
- 最多展示 5 条核心视频，不因达到数量而加入弱证据；
- 每个 `V` 标签包含标题、平台、链接、时间戳、观看理由和观看重点；
- 同一来源镜像不重复计数；
- 无法确定唯一原因时使用条件化语言，并提出一个最能改变答案的澄清问题；
- 器材、疼痛或伤病问题保持证据与安全边界，不把视频内容扩张为医疗结论。

### 11.3 兼容与回退

v3 某主题未发布足够证据时，路由器可以明确选择完整的 v2 路径；不能在同一条主张中混合 v3 正式证据与 v2/raw 候选来填空。answer packet 必须记录所用运行时版本和回退原因。

## 12. 质量与评测规格

### 12.1 构建硬门禁

以下任一失败都阻止 publication 或 release：

- 私有路径、完整转写、媒体、密封问题或审核草稿泄漏；
- 内容哈希、schema、引用完整性或状态机不一致；
- `published` 主张没有有效 teaching event；
- teaching event 未绑定当前正式投影或缺少所需的语言/视觉审核；
- 自动工具被记录为领域审核者；
- 来源身份、canonical URL、镜像或时间范围无效；
- 运行时构建不可复现；
- 当前 v2 确定性基线出现回归。

### 12.2 回答硬门禁

在 development 与 sealed holdout 中，以下关键错误必须为 0：

- 术语或事实意义反转；
- 无证据因果关系；
- 使用 forbidden claim；
- 发明训练方法或用户未提供的观察；
- 跨主张转移证据；
- 错误 `V` 映射、裸链接或展示未实际使用的视频；
- 把候选、过期或未发布内容写进答案。

支持视频展示率、引用映射完整率和“为什么看/看什么”完整率必须为 100%。

### 12.3 首批评测集

- 70 条 development cases；
- 30 条仅本地保存的 sealed holdout cases；
- 合计至少 40 条来自真实或历史用户表达，而非纯模板生成；
- 六类主题分别报告，不允许平均分掩盖单一主题失败；
- 必答主张召回率目标不低于 90%；
- frame 关键字段准确率目标不低于 95%；
- 模型评审只能作为诊断信号，不能替代确定性门禁或人工领域批准。

所有比例同时报告样本数和 95% 置信区间。对“0 次关键错误”只陈述本次样本中未观察到错误，并报告上界，不宣称真实错误率为零。

### 12.4 v2/v3 对照

对同一密封问题做配对盲评，至少比较：

- 诊断是否抓住真实问题；
- 技术结论正确性；
- 条件/排除边界；
- 来源与时间戳可验证性；
- 建议是否具体且没有发明；
- 答案是否在缺证据时诚实停下。

v3 不能仅凭总分更高发布；任一关键意义反转、无证据因果或错误引用均为阻断项。

## 13. 成熟开源项目调研与取舍

| 项目 | 借鉴设计 | 本项目明确不采用 |
| --- | --- | --- |

| [Subtitle Edit](https://github.com/SubtitleEdit/subtitleedit) | 本地离线、视频播放、字幕编辑、自动备份与用户掌控文件 | 不复制完整桌面字幕编辑器；只实现本项目审核所需的时间轴能力 |
| [WhisperX](https://github.com/m-bain/whisperX) | VAD、词级 forced alignment 和批量转写可作为时间对齐候选 | 对齐结果不是事实；不自动继承为正式时间戳或逐字稿 |

| [Haystack](https://github.com/deepset-ai/haystack) | 检索、路由、过滤、组合和生成之间的显式模块边界与可追踪数据流 | 不引入通用 RAG 框架；运行时继续保持小型、离线、确定性 |
| [Ragas](https://github.com/vibrantlabsai/ragas) | 数据集驱动评测、测试集生成与持续反馈闭环 | 不把 LLM-as-judge 当发布权威，不启用默认遥测 |
| [FiftyOne](https://github.com/voxel51/fiftyone) | 可筛选的数据集视图、错误切片、视频/标签联合检查 | 不引入 MongoDB、完整视觉 AI 平台或嵌入服务 |

综合结论：借鉴这些项目的**边界和工作流模式**，不直接引入它们的重型运行架构。v3 继续以 Python 标准库、SQLite、静态 HTML/CSS/JS 和显式 JSON/SQL schema 为主，除非后续基准证明新增依赖能显著提高审核正确率或维护效率。

## 14. 技术架构边界

建议分为五个可独立测试的层：

1. `v3_core`：纯数据模型、规范 JSON、哈希、状态机与失效传播；
2. `v3_pipeline`：发现、媒体、ASR、候选、对齐和阶段 manifest；
3. `v3_review`：本地账本、审核 API、静态 UI 和净化导出；
4. `v3_build`：publication 校验、只读 SQLite、索引和 release inventory；
5. `v3_runtime`：query frame、claim retrieval、answer packet、渲染和审计。

约束：

- 业务规则放入可静态导入、可单测的叶子模块；
- CLI 只负责参数、I/O 和编排；
- 所有写入采用临时文件 + 原子替换，账本采用事务；
- 生成物包含 schema/rule/code/input/output 指纹；
- Windows 不依赖 Unix-only 锁、路径或 shell 行为；
- 公开 Skill 仍可直接复制安装，不要求启动审核服务或安装转写依赖。

## 15. 迁移策略

### M0：规格冻结

交付本 Spec、词汇表、数据边界和三项待确认决策。用户确认前不实现会改变回答质量语义的代码。

### M1：证据脊柱

实现 schema、内容身份、append-only ledger、状态机、失效传播、私有泄漏扫描和空 publication。此阶段对 v2 回答零影响。

退出条件：纯函数/数据库契约测试通过；同输入可复现相同 fingerprint；旧 v3 代码没有被整包导入。

### M2：一个完整垂直切片

选择 1 条代表性视频，走通媒体 → ASR → 校正 → 完整性确认 → 教学事件 → 领域主张 → publication → shadow answer。

退出条件：任何源文本/时间修改都会使下游对象失效；本地 UI 可恢复草稿；发行包无私有数据。

### M3：六类试点

建立全局来源路由和六类审核队列；优先覆盖现有真实问题和 v2 高价值证据，不按数量凑主张。

退出条件：每类都通过独立门禁；30 条密封问题完成配对盲评；关键错误为 0；无 v2 确定性回归。

### M4：影子运行与原子切换

v2/v3 同问对照，记录 claim、证据、边界和耗时差异。六类共同通过后一次切换，并保留可回滚的 v2 runtime。

### M5：全量迁移

按风险和用户问题价值扩展到 959 条来源。每批都可单独构建、审核、撤销和复现。

退出条件：959/959 有明确输入与审核状态；所有正式内容来自当前有效投影；全量发布门通过后才移除 v2。

## 16. 完成定义

v3.0 只有在以下条件同时满足时才算完成：

- 本 Spec 的待确认决策已关闭；
- 六类试点和全量来源达到约定迁移范围；
- 正式回答不读取 raw ASR、候选、旧状态或私有账本；
- 所有 `published` 主张可追溯到经原视频核对的教学事件；
- 修改传播、失效和撤回可被确定性测试证明；
- 本地审核台通过可用性与恢复测试；
- 私有/公开边界、许可说明和发行清单通过审计；
- Python 3.10/3.12、macOS/Linux/Windows 契约通过；
- v2/v3 配对评测和所有发布门通过；
- 新安装、升级、回滚、doctor、SBOM、签名标签和 release attestation 全部验证。

## 17. 已确认的三项决策

这三项会直接改变 Skill 的回答质量或证据覆盖。用户已于 2026-08-31 全部确认：

1. **正式转写门槛**：修正后的转写必须同时满足逐段校正和完整播放对应原视频；仅自动纠错或逐段覆盖不能算正式转写。
2. **公开发行边界**：完整正式转写只保存在私有维护平面，公开 Skill 只发布已批准主张和最小证据窗口，以降低版权、体积和误用风险。
3. **试点切换方式**：六类试点在 shadow 中分别评测，但只有六类全部通过后才整体切到 v3；未覆盖主题继续使用 v2，避免复合问题混用两套证据语义。

涉及这些语义的后续变更必须通过新 ADR 和明确复核，不以普通重构 PR 静默修改。
